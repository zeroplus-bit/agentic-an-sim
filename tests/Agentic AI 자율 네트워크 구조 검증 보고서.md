# Agentic AI 자율 네트워크 구조 검증 보고서

Nov 18, 2026 · @Yangjung Kim

## 요약 및 종합 판정

현 구조는 부하 급증(셀 용량 초과 포함)과 셀 장애를 사람 없이 1\~4초 안에 탐지하고 2\~3초 안에 복구합니다. 끝나면 자원을 돌려놓고, 세 계층은 설계서의 SN/NR 신호 절차대로 상호작용합니다. 모델링된 장애 범위에서는 세 목적을 달성했습니다. 다만 검증이 낙관적인 트윈에서 이루어졌고 다룬 장애 유형도 제한적이라, 실망 수준에서 "충분하다"고 단정하기는 이릅니다. 검증 과정에서 결함 7건을 고쳤고, 이웃 셀 부하 분산을 추가했습니다. 아래 판정은 최종 코드 기준입니다.

| 목적 | 판정 | 핵심 수치 (최종) | 남은 한계 |
| --- | --- | --- | --- |
| 망자원 효율 분배 | 충족 (단, 낙관적 트윈) | 정상 시 SLA 충족률 1.0. 급증 후 몫과 이웃 셀로 옮긴 몫이 모두 원래 수준으로 복귀 | 셀 PRB 사용률 0.60\~0.65로 목표 0.7\~0.9 미달. 급증 여유를 보지 않고 선등록. 트윈과 제어기가 같은 수요 법칙을 씁 |
| 장애 자동 해결 | 충족 (모델링된 장애) | 탐지 1\~4초, 회복 2\~3초. 장애 중 충족률 0.95\~0.98 (수정 전 eMBB 0.02, URLLC 0.72) | 컴퓨팅·전송망·에이전트 장애는 미검증. 이웃 셀까지 부족하면 부분 수용 |
| 사람 개입 최소화 | 충족 | 보정 에이전트가 동작하는 6개 시나리오에서 사람 판단 필요 0건 (수정 전 4개 시나리오에서 발생) | 자동 결정은 규칙 기반. 우선순위 1\~2 성능 저하와 에이전트 부재는 사람 검토 |
| (추가) 계층 간 신호 절차 | 충족 | 의도 생애 전체 337개 메시지가 참조점·카탈로그·순서·요청/응답 검사 8개를 모두 통과 | 없음 (traceId 전파 수정 완료, 검사 8개 통과) |

- **자율 수준:** 3GPP TS 28.100 기준으로 조건부 자율(L3)을 넘어, 여러 셀에 걸친 폐루프까지 스스로 돌리는 수준에 근접했다고 판단합니다. 다만 예측적 결정과 분야 간 자율이 없어 L4라고 하기는 어렵습니다.
- **충분한 수준으로 가는 데 필요한 것:** 제어기가 모르는 수요 불확실성을 넣은 재검증, 장애 유형 확대, 급증 여유를 보는 수용 제어의 세 가지입니다.

## 검증 목표와 판정 기준

세 목표를 측정 가능한 지표로 바꾸고, 각 지표에 합격선을 미리 정한 뒤 실험했습니다. 단계 구분은 3GPP TS 28.100(자율 네트워크 수준)의 워크플로 다섯 단계(의도 처리, 인지, 분석, 결정, 실행)를 따릅니다.

| 목표 | 지표 | 합격선 (실험 전 설정) |
| --- | --- | --- |
| 망자원 효율 분배 | 정상 시 SLA 충족률 | 0.95 이상 |
| 망자원 효율 분배 | 장애 해제 후 PRB 몫 원복(스케일다운) | 정상 시 몫 + 1%p 이내로 복귀 |
| 망자원 효율 분배 | 다른 의도에 대한 부작용 | 대상 외 의도 충족률 하락 없음 |
| 장애 자동 해결 | 탐지 시간 (장애 시작 → DEGRADED) | 10초 이내 |
| 장애 자동 해결 | 회복 시간 (DEGRADED → FULFILLED) | 60초 이내 |
| 장애 자동 해결 | 장애 유형 커버리지 | 주입한 유형 모두 자동 회복 |
| 사람 개입 최소화 | 사람 결정 필요 충돌(NEEDS\_DECISION) | 0건, 또는 자동 결정이 타당 |
| 사람 개입 최소화 | 회복 못 하고 끝난 의도 | 0건 |

## 검증 환경과 방법

시나리오마다 3계층(Service·Network·Resource)을 새로 띄우고, 에이전트 메모리도 빈 상태에서 시작했습니다. 시나리오끼리 서로 영향을 주지 않게 하기 위해서입니다.

- **의도 3개:** 병원 원격수술 URLLC(5 ms, 50 Mbps, 99.999%, 우선순위 2), 경기장 4K eMBB(200 Mbps, 50 ms), 항만 스마트 미터 mMTC(5 Mbps, 200 ms). 각각 셀 2개에 배치했습니다.
- **타임라인:** 프로비저닝 → 정상 20초 → 장애 60초 → 장애 해제 후 회복 60초. 1초마다 Network Layer의 의도 상태·PRB 몫·KPI 충족 여부와 트윈의 셀 상태를 기록했습니다.
- **비교 기준:** 같은 응급 상황을 자동 보정 에이전트(agent-assure-01) 없이 한 번 더 돌려, 폐루프가 실제로 기여하는 바를 분리했습니다.

| 시나리오 | 주입한 장애 | 확인하려는 것 |
| --- | --- | --- |
| emergency | URLLC 수요 ×1.4 | 폐루프 탐지·회복, 스케일다운 |
| emergency\_noloop | 위와 같음, 보정 에이전트 제거 | 폐루프의 기여도 |
| special\_event | eMBB 수요 ×1.3 | eMBB 자동 보정 |
| iot\_surge | mMTC 수요 ×1.4 | mMTC 자동 보정 |
| stress\_1.6 | 전체 부하 ×1.6 | 동시 다발 보정, 충돌 |
| cell\_down | gNB-012-1 다운 (병원 셀) | 용량 문제가 아닌 장애의 처리 |
| contention | 응급 + 병원 셀에 URLLC 의도 3개 추가 | 자원 경합 시 자동 결정의 타당성 |

측정 도구는 `tools/verify_autonomy.py`이고, 시나리오별 원자료는 `logs/verify/`에 저장됩니다.

## 결과 1: 망자원 분배 효율

수정 후에는 급증 때 늘린 PRB 몫이 장애 해제 20\~40초 안에 원래 수준(+1%p 이내)으로 돌아옵니다. 수정 전에는 늘어난 몫이 끝까지 남아, 급증이 한 번 지나갈 때마다 셀의 전용 자원이 5\~13.5%p씩 쌓였습니다.

| 시나리오 | 의도 | 수정 전: 정상 → 최대 → 종료 (PRB %) | 수정 후: 정상 → 최대 → 종료 (PRB %) |
| --- | --- | --- | --- |
| emergency | URLLC | 20 → 28 → 28 | 20 → 28 → 20 |
| stress\_1.6 | URLLC | 20 → 33 → 33 | 20 → 33 → 20.5 |
| stress\_1.6 | mMTC | 2 → 7 → 7 | 2 → 7 → 3 |
| iot\_surge | mMTC | 2 → 7 → 7 | 2 → 7 → 3 |
| contention | URLLC (2번째) | 24 → 33.5 → 33.5 | 24 → 33.5 → 24.5 |
| cell\_down | URLLC | 20 → 20 → 20 (조치 없음) | 20 → 28.5 → 20.5 (페일오버 후 복귀) |

- **되돌리기 기준:** 몫은 측정 부하가 슬라이스의 프로비저닝 목표(URLLC 0.72, eMBB 0.8, mMTC 0.85)에 맞는 크기까지만 줄입니다. 처음 충족했을 때의 몫보다 작게는 줄이지 않고, 줄이기 전에 사전 검증을 거칩니다. mMTC가 2가 아닌 3에서 멈춘 것은 급증 때 전용 격리로 격상됐기 때문입니다.
- **부작용 없음:** 모든 시나리오에서 장애 대상이 아닌 의도의 충족률은 1.0을 유지했습니다. 되돌린 뒤 다시 위반이 생겨 롤백된 경우는 0건입니다.
- **합격선과 비교:** 정상 시 SLA 충족률은 모든 의도에서 1.0이고, 스케일다운도 이제 합격선 안입니다.
- **남은 비효율:** 의도를 올린 셀의 평균 PRB 사용률은 정상 시 0.63\~0.65로, 목표 대역 0.7\~0.9보다 낮습니다. 또 경기장 eMBB(200 Mbps)는 프로비저닝 시점부터 셀의 80%를 전용으로 잡아, 급증을 받을 여유가 없었습니다.

## 결과 2: 장애·오류 자동 해결

용량 안에서 해결 가능한 장애는 모두 사람 없이 회복됐습니다. 탐지는 1\~4초, 회복은 2\~19초입니다. 셀 하나의 물리 용량을 넘는 급증(경기장 eMBB)은 수정 후에도 해결되지 않지만, 1\~1.5초 안에 부족분을 수치로 서비스 계층에 알리고 자동으로 부분 수용합니다.

| 시나리오 (대상 의도) | 장애 중 충족률 (전 → 후) | 위반 시간 (전 → 후) | 탐지 | 회복 (전 → 후) | 수정 후 대응 |
| --- | --- | --- | --- | --- | --- |
| emergency (URLLC) | 0.70 → 0.72 | 18 s → 17 s | 1.0 s | 18.4 s → 18.4 s | PRB 20→32%, 종료 후 20%로 복귀 |
| emergency\_noloop (URLLC) | 0.02 → 0.02 | 59 s → 59 s | 1.0 s | 회복 없음 (장애 해제 때까지) | 비교 기준: 보정 에이전트 없음 |
| iot\_surge (mMTC) | 0.98 → 0.98 | 1 s → 1 s | 4.1 s | 2.0 s → 2.0 s | 전용 격리 격상, 종료 후 복귀 |
| stress\_1.6 (URLLC) | 0.72 → 0.72 | 17 s → 17 s | 1.0 s | 18.4 s → 18.4 s | 두 의도 동시 보정 |
| cell\_down (URLLC) | 0.98 → 0.98 | 1 s → 1 s | 1.0 s | **61.4 s → 3.1 s** | 남은 셀 PRB 20→37% (핸드오버 부하 포함) |
| contention (URLLC 2번째) | **0.45 → 0.72** | **33 s → 17 s** | 1.1 s | 33.8 s → 18.5 s | 경쟁 조건 제거로 제때 할당 |
| special\_event (eMBB) | 0.02 → 0.02 | 59 s → 59 s | 2.0 s | 회복 없음 → 회복 없음 | 1.5 s만에 에스컬레이션 (필요 99\~116% > 상한 80%) |
| stress\_1.6 (eMBB) | 0.02 → 0.02 | 59 s → 59 s | 1.0 s | 회복 없음 → 회복 없음 | 1.0 s만에 에스컬레이션 (필요 101\~142%) |

- **폐루프의 기여:** 같은 응급 상황에서 보정 에이전트를 끄면 충족률이 0.02, 켜면 0.72입니다. 자동 보정이 60초 중 42초를 살렸습니다.
- **회복 18초의 내역:** 주로 구조적 지연입니다. 위반 3회 누적 후 탐지, 보정 적용, 이후 충족 샘플 3회로 FULFILLED 전환이 차례로 일어나고, 셀별로 도는 보정 두 번이 겹치기 때문입니다. 60초 합격선 안이지만, URLLC 서비스에게 17초의 위반은 길습니다.
- **용량 한계:** 경기장 eMBB는 급증 때 셀 용량의 99\~142%를 요구해 셀 안에서는 해결할 수 없습니다. 수정 전에는 조용히 실패했고, 수정 후에는 즉시 보고합니다. 실제로 해결하려면 인접 셀 부하 분산이 필요합니다.
- **주입하지 않은 장애:** 컴퓨팅 노드 과부하는 알람이 발생해도 처리하는 경로가 아직 없습니다. 전송망·코어 장애는 트윈에 아예 없습니다.

## 결과 3: 사람 개입 필요 지점

수정 후 7개 시나리오에서 사람이 판단해야 한 사건은 0건입니다. 수정 전에는 4개 시나리오에서 운영자가 직접 알아채거나 처리해야 하는 상황이 생겼습니다.

| 시나리오 | 수정 전 | 수정 후 |
| --- | --- | --- |
| special\_event | eMBB가 59초 위반하는 동안 아무 알림 없음. 운영자가 대시보드로 발견해야 함 | 1.5초에 에스컬레이션, 서비스 계층이 자동 ACCEPT\_PARTIAL로 결정하고 테넌트에 통지 |
| stress\_1.6 | 위와 같음 | 위와 같음 (1.0초) |
| cell\_down | 61초간 DEGRADED. 시도 4회를 넘기면 "서비스 계층 결정 대기"로 멈추지만 서비스 계층에는 아무것도 안 감 | 3.1초에 페일오버로 회복, 개입 필요 없음 |
| contention | 의도 2개 REJECTED, "운영자에게 보고". 그중 1개는 자리가 있는데도 경쟁 조건 때문에 거부됨 | 자리가 있는 의도는 수용. 나머지 1개는 "여유 22% < 필요 24%"라는 사유로 자동 수용 제어 |
| emergency, iot\_surge, emergency\_noloop | 개입 필요 없음 | 개입 필요 없음 |

- **사람을 부르는 유일한 경우:** 우선순위 1\~2인 중요 서비스가 용량 한계로 성능 저하 상태에 있을 때만 humanReview로 표시합니다. 이번 시나리오에서는 발생하지 않았습니다.
- **사람 없이 결정하되, 무엇을 포기했는지는 남깁니다.** 부분 수용은 서비스가 유지되는 최선의 몫으로 계속 돌고, 수요가 줄면 네트워크가 스스로 되돌립니다. 부족분과 결정 사유는 충돌 기록에 남습니다.
- **남은 소음:** 용량 한계가 이어지는 동안 에스컬레이션이 30초마다 다시 나가, 장애 1건에 자동 결정이 2\~3회 기록됩니다.

## 결과 4: 이웃 셀 부하 분산과 회복 시간 단축

이웃 셀 부하 분산(모빌리티 로드 밸런싱)을 넣자, 셀 용량을 넘던 eMBB 급증도 2초 안에 회복했습니다. 부하 추정과 재시도 간격을 고친 뒤에는 URLLC 회복도 18초에서 2초로 줄었습니다.

| 시나리오 (의도) | 장애 중 충족률 | 위반 시간 | 회복 | 에스컬레이션 |
| --- | --- | --- | --- | --- |
| special\_event (eMBB) | 0.02 → 0.97 | 59 s → 2 s | 없음 → 2.0 s | 2회 → 0회 |
| stress\_1.6 (eMBB) | 0.02 → 0.97 | 59 s → 2 s | 없음 → 3.1 s | 3회 → 1회 (일시적 부족 86% > 80%) |
| emergency (URLLC) | 0.72 → 0.98 | 17 s → 1 s | 18.4 s → 2.1 s | 0회 |
| stress\_1.6 (URLLC) | 0.72 → 0.98 | 17 s → 1 s | 18.4 s → 2.0 s | 0회 |
| contention (URLLC 2번째) | 0.72 → 0.97 | 17 s → 2 s | 18.5 s → 3.1 s | 0회 |
| cell\_down (URLLC) | 0.98 → 0.98 | 1 s → 1 s | 3.1 s → 3.1 s | 0회 |

- **부하 분산 동작:** 의도의 몫이 상한(80%)에 닿거나 셀 예산(90%)이 바닥나면, 에이전트가 의도 단말의 최대 40%를 가장 한가한 이웃 셀로 옮깁니다. 이웃은 같은 사이트의 다른 섹터와 인접 사이트의 섹터입니다. 옮긴 단말은 셀 가장자리에 있어 효율 0.85, 지연 ×1.1로 모델링했고, 오직 태인 에스컬레이션은 이웃 셀도 받지 못할 때만 납니다. 수요가 줄면 단말을 되돌리고 이웃 셀의 PRB를 반납합니다(장애 종료 후 남은 몫 0%).
- **회복 단축의 원인:** 기존에는 두 가지가 겹쳤습니다. 부하를 최근 5개 샘플의 평균(급증 이전 값 포함)으로 추정해 첫 보정이 부족했고(20→25%), 두 번째 보정은 15초 재시도 간격을 기다렸습니다. 지금은 최근 3개 샘플의 최대값으로 추정하고, 의도의 다른 셀도 같은 작업에서 보정하며, 재시도 간격은 5초입니다.
- **비교 기준 시나리오:** 보정 에이전트가 없는 경우에는 이제 4회 시도 후 서비스 계층에 에스컬레이션합니다. 우선순위 2인 URLLC라서 사람 검토(humanReview)로 표시됐는데, 이는 설계대로의 동작입니다.

## 단계별 자율성 평가

다섯 단계 모두 모델링된 장애 범위 안에서는 시스템이 스스로 수행합니다. 범위를 벗어나면 분석과 결정 단계에서 자율성이 끊깁니다. 종합하면 특정 시나리오에서 스스로 최적화하는 조건부 자율 수준(L3)에 해당한다고 판단합니다. 이 등급은 표준의 공식 인증이 아니라 검증자의 판단입니다.

| 단계 | 수행 주체 | 근거 | 한계 |
| --- | --- | --- | --- |
| 의도 처리 | 시스템 (애매할 때만 사람) | 발화를 슬라이스와 KPI로 변환(블라인드 세트 정확도 0.867, KPI 완전일치 0.983). 모호하거나 모순되는 의도는 13%의 비율로 되물음 | 평가 라벨이 단독 작성 초안 |
| 인지 | 시스템 | 1초 텔레메트리, 위반·예측·알람 세 경로로 탐지, 1\~4초 | 컴퓨팅 노드 알람은 받지만 처리하지 않음. 전송망·코어는 관측 대상이 아님 |
| 분석 | 시스템 (2가지 원인만) | PRB 부족과 셀 장애를 구분해 다른 대응을 함. LSTM으로 위반 예측 | 그 외 원인은 분석하지 않음. 근본 원인 분석 없음 |
| 결정 | 시스템 (용량 내) / 규칙 정책 (용량 초과) | 몫 크기 계산, 우선순위 선점, 부분 수용 자동 결정 | DQN은 대부분 보상 모델 모드로 동작(학습된 정책 아님). 우선순위 1\~2 성능 저하는 사람 검토 |
| 실행 | 시스템 | 사전 검증 → 적용 → 30초 감시와 롤백, 되돌리기. 적용 6\~23건, 롤백 0건 | 셀 단위 PRB와 이웃 셀 단말 이동(부하 분산)을 제어. 전송망·코어 설정은 없음 |

1. **\[완료 — 결과 4\] 인접 셀 부하 분산:** 셀 용량을 넘는 급증(경기장 eMBB 59초 위반)을 해결할 유일한 방법입니다. 트윈에 셀 간 트래픽 이동을, 실행 단계에 트래픽 조향 조치를 추가해야 합니다.

3. **\[완료 — 결과 4, 18초 → 2초\] URLLC 회복 단축:** 현재 18초(위반 17초)입니다. 탐지 기준(위반 3회)을 예측 기반으로 앞당기고 여러 셀을 동시에 보정해 10초 이내를 목표로 합니다.
4. **\[중간\] 장애 유형 확대:** 컴퓨팅 노드 과부하, 에이전트 프로세스 다운(등록부 장애 조치), 설정 적용 실패, 전송망 지연을 주입하고 처리 경로를 만들어야 합니다.
5. **\[중간\] 급증 여유를 보는 수용 제어:** 셀의 80%를 차지하는 의도는 실현성 질의(SN-05) 단계에서 "급증 여유 없음"을 경고해야 합니다.
6. **\[낮음\] 에스컬레이션 중복 제거:** 같은 장애에 대한 30초 간격 반복 통지를 묶어야 합니다.
7. **\[낮음\] DQN 정책 학습과 비교 평가:** 현재는 보상 모델 모드로 규칙에 가깝게 동작합니다. 학습된 정책이 규칙보다 나은지 별도 실험이 필요합니다.
8. **\[낮음\] 반복 실행:** 시드를 바꿔 시나리오당 10회 이상 돌려 신뢰구간을 내야 합니다.

9) **\[완료\] traceId 전파:** 의도 흐름 전체가 traceId 하나를 공유하도록 SN-01에서 만든 trace를 NR 요청과 알림에 이어 붙여야 합니다.

## 검증의 한계와 해석 시 주의점

이 수치들은 구조의 논리가 맞는지를 보여 주지만, 실망에서의 성능을 보증하지는 않습니다.

- **트윈과 제어기가 같은 수요 법칙을 공유합니다.** 트윈의 의도 수요(요청 대역폭 × 1.15)와 제어기의 몫 계산식(`DEMAND_FACTOR = 1.15`)이 같은 상수를 씁니다. 제어기가 플랜트의 수요 법칙을 정확히 알고 있는 셈이라, 효율·SLA 수치가 낙관적입니다.
- **모델링하지 않은 장애가 있습니다.** 전송망·코어 장애, 컴퓨팅 노드 장애(NODE\_OVERLOAD 알람은 발생하지만 처리 경로 없음), 에이전트 프로세스 다운, 설정 적용 실패는 주입하지 않았습니다.
- **인접 셀로의 부하 분산을 모델링하지 않았습니다.** 셀 용량을 넘는 수요는 다른 셀로 나눌 수 없어서, 용량 한계에 걸리면 에스컬레이션이 유일한 대응입니다.
- **셀 장애 시나리오는 수정 전후 트윈이 다릅니다.** 수정 후에는 죽은 셀의 단말이 남은 셀로 핸드오버되는 부하를 추가해 더 어렵게 만들었습니다.
- **표본이 작습니다.** 시나리오당 1회, 의도 3\~6개이고 난수 시드는 고정입니다. 편차나 신뢰구간은 아직 내지 않았습니다.
- **외부 LLM 에이전트의 결정은 평가하지 않았습니다.** 모든 결정은 내장 규칙 기반 정책으로 내렸습니다.
